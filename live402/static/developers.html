Run the offline guard

Requires Node.js 22 or newer. This uses a public test key and synthetic evidence. No networking, signing or payment occurs.

git clone https://github.com/402signalhq/402signal.git
cd 402signal
node --input-type=module <<'JS'
import { readFileSync } from 'node:fs';
import { verifyRoute } from './sdk/route-guard/index.mjs';
const vectors = JSON.parse(readFileSync('tests/fixtures/route-binding-v1.json'));
const sample = vectors.cases[0];
const terms = verifyRoute({
  routeResponseJson: JSON.stringify(sample.response),
  routeRequestJson: JSON.stringify(sample.request),
  trustedLogVkey: vectors.trusted_vkey, // PUBLIC TEST KEY, not production.
  request: {
    url: sample.response.url,
    method: sample.method,
    body: Buffer.from(sample.body)
  },
  challenge: { status: 402, bodyText: JSON.stringify(sample.challenge) },
  now: sample.now // Fixture only. Omit in a real integration.
});
console.log(terms.model, terms.request.method, terms.accepted.network);
JS

Real integrations must retain raw untrusted JSON rather than parse and reserialize it. The fixture above is trusted local test data.

Hosted check

Call POST /route

Send an unpaid request first. It returns HTTP 402 with the current routing payment requirements. It does not authorize or settle a payment.

curl -sS -D - https://402signal.com/route \
  -H 'Content-Type: application/json' \
  --data '{"need":"web search","networks":["base"],"max_price_usd":0.02,"require_route_binding":true}'

Validate the requirements and reserve your budget in the buyer. Authorize the $0.003 USDC fee with your own wallet, then submit the identical JSON with the resulting PAYMENT-SIGNATURE. Never send wallet private keys to 402Signal.

$0.003 only when a valid live route is found. Normal typed misses are not settled. Seller payment is separate.

Supported exact request bodies

The ordinary guard covers GET and the narrowly justified empty-object POST fallback. The explicit parallel-search-json-v1 profile permits a bounded search request only at https://parallelmpp.dev/api/search. It is not a general POST proxy.

Compatibility observation, September 7, 2026: the Parallel gateway changed its recipient across unsigned challenges, so the current fixed-offer guard refused seller signing. The example below documents a bounded request profile, not a qualified live purchase path for rotating recipients. Do not replace a recipient pin or bypass the refusal.

{
  "url": "https://parallelmpp.dev/api/search",
  "networks": ["base"],
  "max_price_usd": 0.01,
  "require_invocable": true,
  "require_route_binding": true,
  "probe_request": {
    "profile": "parallel-search-json-v1",
    "method": "POST",
    "body": "{\"query\":\"x402 payment protocol\",\"mode\":\"one-shot\"}"
  }
}

The exact body string is bound to the observation. The profile accepts only a nonempty query of at most 300 characters and mode:"one-shot", within 4 KiB, with no arbitrary caller headers. The body is sent only to the designated endpoint and is not broadcast through discovery. This profile is documented for HTTP, not the advertised MCP input schema.

Local buyer guard

Compare the current offer before signing

Set "require_route_binding": true for a signed v4 receipt on supported exact x402 observations. It binds the original route request, exact seller URL, method, body hash and observed offer.

Preserve the original request and raw response. Obtain the seller's current unpaid challenge for the same URL, method and body bytes without following redirects. Use a log verification key from independent trusted configuration, not a key offered by the response being verified.

import { withVerifiedRoute } from '@402signal/route-guard';

await withVerifiedRoute({
  routeResponseJson, routeRequestJson, trustedLogVkey,
  request: { url, method, body: exactRequestBytes },
  challenge: { status: 402, bodyText, paymentRequired }
}, async verified => {
  // Your buyer validates the actual transaction and its durable
  // budget against verified.accepted before its own wallet signs.
});

This is integration scaffolding, not complete wallet code. The reference buyer shows the supported payment lifecycle. The default observation window is 60 seconds; inspect the actual expiry. A valid receipt does not promise that the seller will honor a quote for the entire window.

The callback is a permission boundary in your application. A hosted check or a request flag alone cannot stop your wallet. Your buyer must validate transaction effects, reserve budgets, prevent duplicate seller sends and refuse altered or expired evidence. A valid receipt does not guarantee delivery or output quality, or reverse the routing fee.

verifyReceipt checks historical evidence after expiry without authorizing a new purchase. The x402 adapter for mppx handles supported Base gateway challenges; it is separate from native MPP sessions.

One durable attempt

Recover a lost response without a fresh payment

The client stores the exact request, private recovery credential and authorization before submission. Reopening the same attempt enters recovery instead of silently authorizing another payment.

import { RouteClient } from '@402signal/route-guard/client';
import { FileAttemptStore } from '@402signal/route-guard/file-store';

const client = new RouteClient({
  store: new FileAttemptStore('/private/buyer/route-attempts'),
  recoveryProfile: 'http-route-v1'
});
await client.prepare(attemptId, JSON.stringify({
  need: 'web search', require_route_binding: true
}));
const challenge = await client.challenge(attemptId);
// Your wallet inspects the requirements, reserves the budget and signs once.
await client.setPaymentHeader(attemptId, { value: signedHeader });
const outcome = await client.submit(attemptId);
// After a lost response or restart, use the SAME durable attempt:
const recovered = await client.recover(attemptId);

attemptId and signedHeader come from your application. This snippet does not implement signing or authorize the seller purchase. Do not use automatic-payment middleware, automatic redirects or payment retry wrappers.

Before routing authorization
HTTP 402 supplies requirements. No paid check has completed.
Completed normal miss
A completed normal miss returns HTTP 200 with live:false, payable:false, selected_payment:null and billing.settlement_state=not_attempted. No routing settlement was attempted.
Qualifying offer
Read the offer and billing result together. HTTP 200 alone does not authorize a seller purchase. The fee remains paid when the customer later declines or the guard refuses changed terms.
Operational or uncertain outcome
HTTP 503 can mean incomplete evaluation, required evidence failure after settlement, or unknown settlement. Inspect billing.settlement_state before retrying. Do not reuse an unknown authorization. An unread response is not proof that no payment happened.
Recovery unavailable
Reconcile the original authorization with independent, read-only chain evidence. Keep reserved funds until the outcome is established. Do not generate another payment or a new job ID as a recovery shortcut.

Protect payment headers and attempt stores as sensitive credentials. Optional access credentials identify an integration or workload class; they are not customer wallet keys. The documented recovery-only client profile is HTTP /route, not MCP. Recovery retrieves the original result and expiry; it does not extend the quote or resume seller execution.

Batch offers need their own evidence

An ordinary exact-payment receipt does not authorize a batch or session. The v0.5 client includes a separate v5 batch verifier. The hosted service must explicitly enable the relevant qualified profile.

Treasury, security and platform teams

Keep enforceable policy outside the model.

Let the agent propose a capability or endpoint. Trusted application code should supply enforced limits, approved recipients, verification keys and signing authority. A model-generated request is not an organizational policy system.

Hosted 402Signal check
Evaluates submitted requirements against a supported current offer. Unknown required measurements fail closed. It does not centrally administer your organization's wallet policy.
Local verification guard
Verifies bound evidence, request identity, relevant terms and expiry before its callback. It cannot protect a caller that bypasses the guard or supplies malicious trusted modules.
Buyer and wallet
Enforce durable budgets, recipient allowlists, chain/token/transaction effects and one-shot payment identity. Obtain human approval before the final fresh check when required.
Evidence owner
Retains the original private request and response, reconciles uncertain outcomes and handles internal retention and access control.

The server's destination-change handling is not a permanent organization-wide recipient allowlist. A later independent observation can establish a changed destination. Pin approved recipients in trusted buyer policy when that stronger boundary is required.

There is no hosted approval queue, delegated signer, escrow, delivery guarantee or dispute-resolution service. For volume integrations, confirm workload access and operating limits; shared storage is not a throughput certification.

PQ Trust

Make routing evidence part of the response

Use "require_transparency": true when evidence is required without exact-request binding. Bound routes require their own signed evidence. Inspect pq_trust.transparency rather than equating HTTP success with log inclusion.

Keep the verification record: retain the full paid response, including pq_trust.transparency.receipt and pq_trust.transparency.reveal, plus your original request. Store it privately; do not put it in public logs.

The immediate log receipt uses Ed25519. Cumulative checkpoints use native Falcon-1024 authorization on Algorand MainNet. The route call does not wait for chain confirmation. A pending anchor is not confirmed evidence.

The public log contains commitments, not a recoverable copy of your private decision. Private replay outcomes can retain the reveal for bounded attempt recovery, but are not a long-term evidence backup. Keep your own copy and an independently trusted verification key.

Historical integrity verification does not extend an observation's expiry. It does not authorize or secure the seller payment.
