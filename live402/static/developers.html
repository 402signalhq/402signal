1. Get the advertised routing fee

Call POST /route

Send an unpaid request first. This returns HTTP 402 with the current payment requirements; it does not authorize or settle a payment.

curl -sS -D - https://402signal.com/route \
  -H 'Content-Type: application/json' \
  --data '{"need":"web search","networks":["base"],"max_price_usd":0.02,"require_route_binding":true}'

Validate the returned requirements and authorize the $0.003 USDC routing fee using your buyer's wallet. Submit the identical JSON with the resulting PAYMENT-SIGNATURE. Do not send wallet secrets to 402Signal.

$0.003 only when a valid live route is found. Normal typed misses are not settled. Seller payment is separate.

Install the client and guard

Use the reviewed v0.5.0 release archive, verify its published digest, then install it locally. Node.js 22 or newer is required. This archive is not an npm registry release.

npm install ./402signal-route-guard-0.5.0.tgz

The package exports @402signal/route-guard/client, /file-store, the exact-payment guard and the separate /batch guard. The private file store needs a supported POSIX filesystem, such as the buyer's Linux or WSL environment.

import { RouteClient } from '@402signal/route-guard/client';
import { FileAttemptStore } from '@402signal/route-guard/file-store';

const client = new RouteClient({
  store: new FileAttemptStore('/private/buyer/route-attempts'),
  recoveryProfile: 'http-route-v1'
});

await client.prepare(attemptId, JSON.stringify({
  need: 'web search', require_route_binding: true
}));
const challenge = await client.challenge(attemptId);
// Your wallet checks the quote and budget, then signs.
await client.setPaymentHeader(attemptId, { value: signedHeader });
const outcome = await client.submit(attemptId);

attemptId is your durable, unique operation identifier. signedHeader comes from your own payment code. This example does not implement wallet signing or authorize a seller purchase.

2. State your requirements

What you can send

Discover a capability

{
  "need": "erc20 token balance",
  "networks": ["base"],
  "max_price_usd": 0.02,
  "require_invocable": true,
  "require_route_binding": true
}

Check one endpoint

{
  "url": "https://seller.example/x402",
  "require_route_binding": true
}

A required network excludes other networks; prefer_network only influences ranking. Price, response-time and invocation constraints remain separate. Unknown costs cannot satisfy a required total-cost cap.

Use the free request builder for supported filters, or the OpenAPI schema for the complete contract. HTTP probe time is not settlement latency.

Supported exact request bodies

The ordinary guard covers observed GET requests and the narrowly justified empty-object POST fallback. A separate opt-in profile permits one reviewed search request at https://parallelmpp.dev/api/search.

{
  "url": "https://parallelmpp.dev/api/search",
  "networks": ["base"],
  "max_price_usd": 0.01,
  "require_invocable": true,
  "require_route_binding": true,
  "probe_request": {
    "profile": "parallel-search-json-v1",
    "method": "POST",
    "body": "{\"query\":\"x402 payment protocol\",\"mode\":\"one-shot\"}"
  }
}

The exact JSON string is bound to the observation. This profile accepts only a nonempty query of at most 300 characters and mode:"one-shot", within 4 KiB. It sends that body only to the designated endpoint, with no arbitrary caller headers. It is not a general POST proxy.

3. Verify, then let your wallet decide

Compare the current offer before signing

Set "require_route_binding": true to require a signed v4 receipt for a supported exact x402 observation. The record binds the route request, seller URL, method, exact body hash and complete observed payment offer.

Keep the raw route response and original route request. Immediately before signing, obtain the seller's current unpaid challenge and call withVerifiedRoute with an independently trusted log verification key.

import { withVerifiedRoute } from '@402signal/route-guard';

await withVerifiedRoute({
  routeResponseJson, routeRequestJson, trustedLogVkey,
  request: { url, method, body: exactRequestBytes },
  challenge: { status: 402, bodyText, paymentRequired }
}, async verified => {
  // Your buyer checks the actual transaction and budget
  // against verified.accepted, then signs in its own wallet.
});

The guard verifies the log signature and inclusion proof, request binding, observed terms and freshness. It rejects altered or expired evidence before invoking your callback. The default observation window is 60 seconds; check the receipt's actual expiry.

The callback is a permission boundary in your application, not an automatic payment guarantee. Independently validate the actual transaction, reserve the budget and prevent duplicate seller sends. A valid receipt does not guarantee delivery, establish output quality or reverse the routing fee.

Historical verifyReceipt checks evidence integrity after expiry. It does not authorize a fresh purchase. The x402 adapter for mppx handles gateway challenges; it is separate from native MPP sessions.

4. Retain one attempt until its outcome is known

Recover a lost response without a fresh payment

The durable client records the exact request, payment header and private recovery credentials before its ordinary paid submission. Reopening the same attempt enters recovery instead of silently creating another authorization.

const recovered = await client.recover(attemptId);

Protect the attempt store as private credentials. A payment authorization is sensitive even though it is not a wallet private key. Optional customer access credentials identify an integration; they are not customer wallet keys.

Completed miss
A completed normal miss returns HTTP 200 with live:false, payable:false, selected_payment:null and billing.settlement_state=not_attempted. No routing settlement was attempted.
Operational or uncertain outcome
HTTP 503 can represent incomplete evaluation, a required evidence failure after settlement, or unknown settlement. Inspect billing.settlement_state before retrying. Do not reuse an unknown authorization or treat an unread response as proof that no payment occurred.
Recovery unavailable
Reconcile the original authorization using read-only chain evidence. Keep the reserved budget until the outcome is established; do not generate another seller payment as a recovery shortcut.

Release qualification

Batch offers need their own evidence

Supported profiles: Base batch settlement, Solana MPP push sessions and Algorand two-item atomic groups. Controlled MainNet tests are complete for these profiles, including merchant payments and independently confirmed settlement. These tests use owner-operated lab endpoints. An ordinary exact-payment receipt does not authorize a batch or session.

The separate v5 batch evidence model binds a supported merchant profile, full observed offer and buyer limits. Profile-specific buyer adapters still validate and sign their own transactions.

The routing check is one qualifying API observation at $0.003. Merchant charges, channel deposits, fees and rent remain separate. This is not a promise that arbitrary batches, endpoints or group sizes are supported.

PQ Trust

Make routing evidence part of the response

Use "require_transparency": true when evidence is required without the exact-request guard. Bound routes require their own signed evidence. Inspect pq_trust.transparency rather than treating an HTTP success as proof of log inclusion.

Keep the verification record: retain the full paid response, including pq_trust.transparency.receipt and pq_trust.transparency.reveal, plus your original request. Store it privately; do not put it in public logs.

The immediate log receipt uses Ed25519. Cumulative checkpoints use native Falcon-1024 authorization on Algorand MainNet. The route call does not wait for chain confirmation. A pending anchor is not confirmed evidence.

The public log commits a fingerprint of the private record. Private replay outcomes can retain the reveal for bounded attempt recovery, but are not a long-term evidence backup. Retain your own copy and a trusted verification key.

Checkpoint verification establishes evidence integrity. It does not authorize or secure the seller payment.
