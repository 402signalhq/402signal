First useful result

Watch the guard accept, then refuse.

Run the real exact-x402 verifier with public synthetic Base evidence and a fake authorization callback. No wallet, account, seller request or payment is needed.

Requires Node.js 22 or newer and Git. Cloning needs a network connection; the bundled reference checks do not. Review the checkout before executing code.

git clone https://github.com/402signalhq/402signal.git
cd 402signal
node integration/buyer-checks/run.mjs
node integration/buyer-checks/run.mjs --self-test

Seven named checks cover a matching offer, changed price, recipient, request rules and expiry, plus original and edited historical evidence. A valid offer must reach the fake callback once with the expected terms. Refused offers must never call it. The self-test catches an unguarded adapter and one that refuses everything.

Test your own authorization boundary

Copy the included adapter and connect your actual buyer boundary. Export authorize(options, fakeCallback). Do not wrap a separate verifier around a production path that bypasses it.

node integration/buyer-checks/run.mjs \
  --adapter ./integration/buyer-checks/example-adapter.mjs

The runner measures the supplied callback and records fixture and top-level adapter hashes. Custom adapters are trusted code, not sandboxed code. Use synthetic inputs in an isolated environment without production credentials, funded signers or external network access.

This pack covers exact-x402 fixtures and historical receipt integrity. It does not test native MPP, continuation, invoices, real settlement or Falcon anchors.

Add a check to your existing buyer

Use this when you have a supported exact-payment endpoint or need a candidate under your buyer's requirements. Your application keeps its wallet, transaction validation and durable budget.

1. Get the checking-fee requirements

curl -sS -D - https://402signal.com/route \
  -H 'Content-Type: application/json' \
  --data '{"need":"web search","networks":["base"],"max_price_usd":0.02,"require_route_binding":true}'

This unpaid request returns HTTP 402, not a completed offer check. For a known endpoint, use url instead of need. The request builder preserves exact URLs and validates sub-cent limits.

2. Complete the authorized check

Your buyer validates the requirements, reserves its budget, and authorizes the $0.003 USDC fee once. Submit the identical request with its PAYMENT-SIGNATURE. Retain the original request and full raw response. Completed normal no-match results are not settled.

3. Compare before seller authorization

Obtain the current seller challenge for the same request without redirects. Verify the bound evidence using a log key from independently trusted configuration. Then let your own payment code validate and authorize the transaction.

import { withVerifiedRoute } from '@402signal/route-guard';

await withVerifiedRoute({
  routeRequestJson, routeResponseJson, trustedLogVkey,
  request: { url, method, body: exactRequestBytes },
  challenge: { status: 402, bodyText, paymentRequired }
}, async verified => {
  // Your existing buyer validates transaction effects and
  // claims its durable budget before its own wallet signs.
});

This is the integration boundary, not complete wallet code. Use the reference Base buyer for a complete supported lifecycle. It requires Node 24 and private POSIX storage. Plan first; do not load a funded signer just to try the example.

Installation and request compatibility

The guard requires Node 22 or newer. Install the matching reviewed release archive after checking its published digest. A package name does not establish an npm registry publication.

sha256sum --check SHA256SUMS
# Install the exact archive whose digest you just verified.

The root guard is offline. /client and /file-store add HTTP recovery and private POSIX persistence. Preserve raw untrusted JSON, not a parsed and reserialized replacement.

Ordinary hosted binding covers supported GET requests and the narrowly defined empty-object POST fallback. The HTTP-only parallel-search-json-v1 profile is restricted to its named endpoint and strict body format. The earlier Parallel example encountered rotating recipients and was refused. Do not replace a recipient pin to make an example work.

networks excludes other rails. prefer_network ranks within the permitted set. max_total_cost_usd means seller price plus known seller-side fees, not a wallet-wide budget including the checking fee. max_latency_ms is HTTP probe time, not settlement time.

Sessions and funding

The call price is not the deposit

Use the session client for supported Base x402 batch channels or native Solana MPP push sessions. Verify the original observation before funding, then pin a separate continuation policy: endpoint, parties, chain, asset, per-call price, cumulative amount, call count and deadline.

The client supports 1 to 64 sequential calls and a fixed buyer deadline up to 24 hours. These are controller bounds, not a throughput promise or evidence of a 24-hour external campaign. Node 24 and private POSIX/SQLite storage are required by the bundled ledger.

A later challenge does not refresh the original observation or buy another routing check. Continuation cannot create a top-up, deposit or new routing authorization. Uncertain signing or sending stops subsequent calls.

Check these limits before integrating

Base activity is serialized for a receiver/token pair. A settled receiver can be reused with its exact accounting baseline; unrelated concurrent receiver activity can leave confirmation unknown. This is not a general multichannel settlement coordinator.

Solana supports push sessions, not pull delegation or automatic funding. Its session cap and minimum voucher increment are not a per-call price. The observed per_call_amount_atomic can be null; pin the service price independently.

Receipt recovery needs a genuinely read-only merchant lookup. Repeating a voucher with a replay-looking header is not safe without an implemented contract. Without verifiable recovery evidence, the attempt stays uncertain.

A local request-body policy does not broaden hosted POST probing or establish merchant-enforced cryptographic body binding.

Algorand manifests

A group is not the same as an invoice

The atomic profile covers 2 to 15 job payments plus a sponsor transaction. The aggregate-invoice profile covers 2 to 64 jobs represented by one invoice payment plus sponsorship. Individual job price allocation in the aggregate invoice is unknown unless separately established.

The merchant must implement the explicit manifest. Bind exact items, recipient, total, hashes and sponsor terms before authorization. Chain atomicity does not promise atomic HTTP delivery.

Billing and recovery

A timeout is not permission to pay again

Use the same durable attempt after a lost response or restart. Reopening it must not silently obtain another authorization. Protect the payment header and recovery material as credentials.

Unpaid HTTP 402
Checking-fee requirements, not a completed paid check.
Completed normal miss
HTTP 200 with live:false, payable:false, selected_payment:null and billing.settlement_state=not_attempted. No routing settlement was attempted.
Qualifying offer
The $0.003 fee pays for the observation. A later refusal or decision not to purchase does not refund it. Seller payment is separate.
Unknown or operational failure
Read billing and the original attempt. HTTP 503 can include incomplete evaluation, a required-evidence failure after settlement, or uncertain settlement. An unread response is not proof the check was free.

Recovery retrieves the original result and expiry. It does not extend the quote or execute the seller purchase. Keep funds reserved while an outcome is unknown. Use independent read-only evidence when the supported recovery path cannot resolve it.

Pick the interface your client actually supports

POST /route supplies HTTP checking and recovery. Node packages provide local verification and optional buyer workflows. MCP exposes only the inputs declared in its manifest.

preview discovers listings; validate checks one exact listed endpoint. Paid route completion needs a capable payment client. The credential-free Glama stdio adapter returns an unpaid challenge but cannot sign or finish a paid route.

Do not infer bounded POST, native charge, batch/session or recovery arguments from HTTP guides when the MCP manifest does not declare them.

Keep enforceable policy outside the model

The agent can suggest an endpoint. Trusted application code supplies approved recipients, spending limits, verification keys and signing authority. 402Signal checks the rules it receives; it cannot establish that a human approved them.

Retain approved policies separately from the submitted request. Correlate the observation with wallet and execution records when investigating a purchase. An action that bypasses 402Signal is outside its log's view.

There is no hosted approval queue, delegated signer, delivery insurance or universal agent-action monitor. A local guard cannot protect a buyer that bypasses it.
